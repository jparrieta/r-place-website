The yard, file by file

The coding yard is where the coder instrument runs over the census: one folder per community, and around them the files of the agent that runs the yard, the scheduler (in this study, a coordinator in Codex). This repository ships the yard as it stands before a run: the scheduler's protocol, its tools, and the case lead's instrument, with the fourteen coded rooms of the Armenia and Dutch example and twelve of their case leads' saved sessions. It does not ship what a running yard writes about itself: the queues, the logs, the progress reports. Everything below links to coder/.

Read first, if you are the yard's handler

  1. CONTRACT-scheduler.md: the scheduler's contract. What it launches, in what order, what it checks, what it may never do, and what is the PI's to decide (page).
  2. README.md: the yard itself, and how to run a room from any agent runner.
  3. CODING-SCHEDULER.md: the coding queue's rules: smallest first by the 97-hour item count, 500 to 50,000 items, how many rooms at once and why, which model and effort.
  4. BRIEF-COORDINATOR.md: the brief queue's runbook, step by step, with the brief writer's prompt.
  5. CASE-LEAD-PROMPT.md: the message added for each case lead (page).
  6. REPAIR-QUEUE-RESTART-RULES.md: how to restart the repair queue, beginning by rebuilding "reality from the filesystem, not from stale memory".
  7. CHECKPOINTS.md and VERIFIED-RUN-ARCHIVES.md: saving, resuming and forking a case lead (page), and packing and restoring a verified room.

How to fill it

  1. Get the raw record of a community: its raw24 file (see data and collection).
  2. Build its room, from your own copy of coder/: python3 _tools/build_room.py --sub <sub> --raw <raw24 folder>/<sub>.jsonl --out rooms/<sub> --instrument _instrument/v32 (add --brief to bring an existing brief). It writes rooms/<sub>/ with ROOM.md, the record cut to the window, the week before, and STATE.json.
  3. Run it: by hand, with the commands in the room's ROOM.md; or through the queues, as the scheduler's contract describes.

How the scheduler remembers, and saves sessions

The scheduler keeps nothing in its conversation it cannot rebuild. Its state is in the queue files, with every event logged beside them, and a restart begins by rebuilding the state from the files on disk (the repair rules). Each room's state is in its STATE.json, rewritten from the room's files; STATUS.tsv is rebuilt from all of them. Only the case lead keeps a saved conversation: codex_lead.py checkpoints it after every reply, and lead_archive.py packs it when the room is done (how the case lead remembers).

Running a yard elsewhere

The yard runs from any machine with python3, zstd and Codex. Three scripts name folders on the author's machine and must be pointed at yours before use:

  • _tools/coding_queue.py, line 16, LEGACY_TOOLS: the earlier coder tools;
  • _tools/sync_briefs_to_source.py, lines 15 and 16, STAGE and SOURCE: where finished briefs are copied;
  • _tools/update_coding_progress.py, line 42, outputs: where the progress report is also written.
